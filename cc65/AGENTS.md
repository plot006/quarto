# Repository Guidelines

cc65 は 6502 系クロス開発スイートです。貢献作業を円滑にするため、本ガイドラインを参照し、既存のフローに合わせた作業を行ってください。

## プロジェクト構成とモジュール整理
- `src`: コンパイラ、アセンブラ、リンカなど主要ツールを格納。コンパイラ変更時は関連ユーティリティも確認。
- `libsrc`: ターゲット別ランタイムとライブラリ実装。新規 API では `include/` のヘッダ定義と整合させること。
- `doc`: ユーザ文書と HTML 生成ソース。生成物はコミットせず `make doc` で再生成。
- `samples` / `targettest`: 実機向けサンプルとプラットフォーム検証スクリプト。新ターゲット追加時は両方を更新。
- `test`: 回帰テストハーネスと期待値。差分が生じた場合は原因を PR 説明に明記。
- `.github/checks`: スタイル検証と補助スクリプト群。CI 失敗を防ぐためローカル実行を推奨。

## ビルド・テスト・開発コマンド
- `make all`: ツール、ライブラリ、ドキュメント、サンプルを一括ビルド。最初の動作確認として実行。
- `make bin` / `make lib`: それぞれバイナリツール群、ライブラリのみを生成し、開発対象を絞れる。
- `make test`: `test/` 以下の回帰テストを実行。バグ修正やコード生成変更時は必須。
- `make check`: `.github/checks` のスタイル検証に加え `src test targettest samples` を連鎖実行。PR 前の最終確認。
- `make clean`: 各モジュールの生成物を削除。異なるターゲット間で再ビルドする際に使用。

## コーディングスタイルと命名規約
- `.editorconfig` に従い UTF-8、LF 終端、スペース 4 個インデント、行末の空白禁止。
- 識別子は標準で予約された接頭辞を避け、公開シンボルは C では二重アンダースコア、アセンブリでは三重アンダースコアを付与。
- 16 進数は大文字表記、ゼロページは 2 桁、その他は 4 桁で統一。非 ASCII 文字の利用は極力避ける。

## テストガイドライン
- `test/` の期待値を更新する場合は変更理由と影響範囲を PR で説明し、関連ターゲットのサンプル実行結果を確認。
- `targettest platforms` と `samples platforms` は代表的ハードウェア構成でのビルド確認を行うため、ターゲット追加時に実施。
- 新規ユーティリティは短い自己検証サンプルを `samples/` に追加し、再利用性を高めること。

## コミットと PR ガイドライン
- コミットメッセージは一行 72 文字以内の英語命令形を推奨し、例: `Apple2: Add file_set_type()` のようにターゲット名 + 概要で始める。
- 各コミットは論理的に独立させ、分割に迷う場合は関連ファイル単位でスコープを決める。
- PR 説明には変更背景、テスト結果 (`make test` など)、関連 Issue 番号を記載。見た目変更はスクリーンショットやログを添付。
- CI 失敗時は再実行に頼らずローカルで `make check` を通し、差分の根本原因を修正してから再プッシュ。

## 追加リソース
- `Code_of_Conduct.md` と `Contributing.md` を必ず参照し、不明点は GitHub Discussions もしくは mailing list (`doc/mailing-lists.txt`) で相談。
- 環境変数 `PREFIX` / `DESTDIR` を設定すると `make install` が機能。配布用スナップショットには `make zip` を利用。
